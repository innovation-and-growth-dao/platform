# Code audit — July 2026 (bugs found, fixes applied, open findings)

A focused audit of the fund-critical flows: round lifecycle (VOTE → **TALLY** → FUNDING),
DRep **rewards** (calc + payout), **skin-in-the-game** pledge + pledge return, milestone
funding + stop-funding, and the **board-election multisig migration**. Verified against the
code (file:line refs current as of 2026-07-03); each item below was confirmed by reading the
actual code paths, not speculation.

## ✅ Fixed in this audit (covered by tests)

| # | Severity | What | Fix |
|---|---|---|---|
| F-1 | HIGH | **Recompute deleted reward entries linked to a pending payout** → the pending multisig tx could still broadcast (funds leave, nothing stamped paid) and the recomputed calc would queue the same recipients again = double payment. | `clearCalc` now refuses when any entry has `payoutActionId` (rewards.service). Test: `test-tally-rewards`. |
| F-2 | HIGH | **Entries could be stamped paid by a tx with no output for them** (recipient cleared their address / override zeroed after linking) — paid entries are immutable, so they could never be paid later. | The confirm-time stamping loop skips address-less / zero-amount entries (multisig-broadcast.service). |
| F-3 | HIGH | **Manual payout confirmation (`submitPayoutTxHash`) skipped every side effect**: milestone never stamped PAID, pledge return never triggered (silently stranded pledge — no later trigger exists). | Manual path now mirrors the platform-broadcast path: stamps `milestone.paidAt/paidInTx` + calls `maybePrepareReturn` (treasury.service). |
| F-4 | HIGH | **A stop-funded (FAILED) proposal could keep drawing payouts** — `submitPoa` / `maybeDecide` never checked `proposal.status`; approving the last milestone even resurrected FAILED → COMPLETE. | `submitPoa` requires status APPROVED; `maybeDecide` re-checks status before preparing the payout / flipping COMPLETE (milestones.service). |
| F-5 | MED | **A board-cancelled (FAILED) milestone payout dead-ended the milestone forever** — the idempotency check counted FAILED actions as "existing". | `preparePayoutAction` ignores FAILED actions (matches the partial-unique-index design). |
| F-6 | MED | **Concurrent witnesses could clobber CONFIRMED → READY**: if two signers raced and the loser's duplicate submit failed, the catch downgraded the already-paid action back to signable. | The failure path never downgrades a CONFIRMED action (`updateMany` with `status: { not: 'CONFIRMED' }`). |
| F-7 | MED | **Concurrent "Prepare payout" could double-link / orphan entries.** | `preparePayout`'s link `updateMany` now guards `payoutActionId: null`; overrides are blocked while an entry is in a pending payout (`setOverride`). |
| F-8 | MED | **All-returning-members board rotation stalled forever** — assembly was only triggered by `submitKey`, but a board whose every member's key carries over has nothing to submit (the UI even promised "assembles on the next status refresh"). | `status()` opportunistically calls `tryAssemble` (cheap no-op when not ready) (board-multisig.service). Test: `test-multisig-migration`. |

Also in this pass: the **service-level e2e suites were repaired** — 13 of 21 had rotted
against intentional validation changes (mandatory Telegram/email contact, expert
conflict-of-interest, milestone `title` min-words, proposal title min-length, ranked
quick-poll voting API, removed `extendVoting`, `ignoreBudgetChange`/`requireFeeTopUp`
round-flag defaults, slimmed submission-anchor shape). All 21 + 2 new suites now pass.

## ⚠ Open findings (listed, NOT yet fixed — prioritize with the team)

### Tally / stage flow
1. **HIGH — Legacy `DV`-status rounds skip tally crystallization**: `transitionTo` only runs
   `finalizeRound` when `round.status === VOTE`; `advanceDueStages` auto-advances legacy `DV`
   rounds to TALLY without finalizing (no decisions, no budget-cut, no polls), and
   `confirmStage`/`launchNextStage` don't map DV→VOTE in `nextStatusOf` so the board can't
   advance manually either. Only relevant if any legacy `DV` round is still live.
2. **MED — `finalize()` mid-vote guard misses the `DV` alias** (blocks only `VOTE`), so a
   legacy round can be finalized mid-vote with implicit-NO for everyone who hasn't voted.
3. **MED — direct VOTE→FUNDING jump bypasses the open-quick-poll guard** (guard only fires
   from TALLY): the round can land in FUNDING with unresolved tie-breaks.
4. **MED — `optIn` can mutate the electorate during TALLY** (checks proposal stage, not round
   status): a board member opting in after voting closed changes totals/denominator of the
   result later anchored by a quick-poll resolution.
5. **MED — manual `finalize-dv` during TALLY bypasses an open quick poll** (approves on
   threshold, ignoring the budget the poll arbitrates) and the poll later re-finalizes the
   same proposal with a forced outcome — possible flip of an already-anchored decision.
6. **LOW — tie detection runs on 2-decimal-rounded powers** (result() `round2`) with a 1e-9
   epsilon: scores that differ by <0.005 collapse into a spurious "exact tie" quick poll,
   inconsistent with the un-rounded Borda math on the poll side.
7. **LOW — `votingResults` double-counts a candidate's quick-poll power across a resolved
   parent poll + a live follow-up poll** (display ordering only).
8. **LOW — quick-poll participation mixes cast-time power with live eligibility power** —
   participation % can exceed 100% or wrongly trigger an extension.

### Rewards / merit
9. **MED — payout tx body is frozen at first sign, but records/anchors read current DB
   values**: address/override changes in the gap make the on-chain anchor contradict the
   actual payment. (Partly mitigated by the new `setOverride` guard; address edits by the
   recipient remain possible.) Proper fix: freeze recipient+amount on the action at prepare
   time and read those at confirm/anchor time.
10. **MED — filtering reward pool counts fees that were never collected** (`submissionFeeAda`
    summed over all proposals incl. REJECTED/unpaid ones).
11. **MED — collective board merit penalties (BOARD_REWARD_LATE / BOARD_PAYOUT_LATE) hit
    members seated AFTER the lapse** (sweep resolves current seats; idempotency is per drep,
    so each new joiner is penalized once for old events).
12. **MED — milestone rewards can only be paid once per round** despite the "monthly" design:
    once any entry is paid, recompute is refused and later review months can't be added.
13. **LOW — D&V bonus rounding can overspend the pool by ~N/2 lovelace** (independent
    `Math.round` per entry) and loses precision above ~9M ₳ (`Number(bigint)`).
14. **LOW — merit idempotency is check-then-create** without a DB unique on
    `(drepId, reasonCode, referenceId)`; concurrent confirms can double-award, and the hourly
    sweep has no overlap guard.
15. **LOW — a relayed witness credits the submitting user** (signature row + TX_SIGNED merit
    + anchor "signers" name the relayer, not the key owner).

### Pledge / milestones
16. **MED — stop-funding doesn't cancel already-prepared PROJECT_FUNDING / PLEDGE_RETURN
    actions** and nothing downstream re-checks proposal status at broadcast time: the board
    can still sign and pay a terminated project's queued payout. (New POAs are now blocked —
    F-4 — but pre-existing queued actions remain signable.)
17. **MED — PLEDGE_RETURN dedupe is application-level only** (no partial unique index like
    PROJECT_FUNDING has); a concurrent double-confirm can queue the same return twice.
18. **MED — `payoutAddress` can be cleared post-submission** → milestone payout action created
    with `destAddress: null` → unbroadcastable, and no endpoint can set it later.
19. **MED — any board member can vote on any milestone POA** (the "fill a MISSING reviewer
    seat" rule isn't enforced — 3 board YES can approve with zero assigned-reviewer votes).
20. **LOW — pledge REJECT doesn't reset `pledgeSeenOnchainAt`**, so the corrected pledge tx
    never re-notifies the board (manual confirm still possible).

### Multisig hand-over
21. **LOW — migration anchors/amounts use the balance at action-creation time**; if the old
    wallet's balance changes before broadcast, the recorded amount is stale (the tx itself
    always empties the address correctly).
22. **LOW — a Koios/db-sync balance hiccup during assembly silently skips the auto-migration**
    (the manual "Migrate funds" button remains as the fallback).

# Addendum — persona-driven e2e pass (2026-07-09)

Three persona-driven scenario suites were added (proposer / voting DReps at scale / board
member), driving the platform end-to-end with 12 registered DReps, non-default round + global
configuration, and — for the board — the **real 3-of-5 signing ceremony** (genuine Ed25519 keys
generated in-test, real CSL-built Cardano transactions, real signature verification; only the
final Koios broadcast and UTxO/parameter reads are stubbed).

## Fixed in this pass

| # | Severity | What | Fix |
|---|---|---|---|
| A-1 | FEATURE GAP | **No escalation when a milestone is rejected repeatedly** — a team could resubmit POAs forever; the only stop was a manually-proposed stop-funding vote. | New global config **`MILESTONE_MAX_REJECTIONS`** (default 3, 0 = off, editable in Platform setup): on the Xth rejection the platform **auto-opens a stop-funding proposal** (proposer role `PLATFORM`) for the normal board 1p1v vote. Covered by `test-proposer-journey`. |
| A-2 | MED | **Milestone rejection counter only counted rejections when a deadline existed** (`autoExtendedCount` was incremented inside the deadline-extension branch) — deadline-less milestones had no rejection history, so the A-1 threshold could never fire for them. | The counter now increments on EVERY rejection; the deadline shift still applies only when a deadline exists. |
| A-3 | MED | **D&V threshold fallback skipped the round's configured value**: `result()` / `votingResults()` fell back from the per-proposal stamp straight to the PLATFORM default (67 %), ignoring the round's `dvApprovalThresholdPct`. An unstamped proposal in a 60 %-round evaluated at 67 % — enough to flip a 64 % outcome, exactly what the at-scale suite hit. | Fallback order is now: per-proposal stamp → round setting → platform default. |

## Documented behaviors worth a design review (not changed)

1. **`dv.vote()` refreshes the voter's snapshot power with merit-adjusted LIVE power at cast
   time** — two DReps with identical snapshot power can contribute different weight depending on
   WHEN they vote (merit earned mid-round raises the later vote). Near a threshold or an exact
   budget-cliff tie this changes outcomes. If snapshots are meant to freeze the electorate, the
   cast-time refresh contradicts it; if live power is intended, the snapshot display is misleading.
2. **`approvalThresholdPct` is stamped only by the filtering advance** — any future path that
   moves a proposal to D&V without `filtering.maybeDecide` must stamp it too (the A-3 fix makes
   the fallback correct, but the stamp is what the anchors record).
